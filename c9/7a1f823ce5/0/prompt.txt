* 真正开始生成 archive 前写入 `automaticBackupInProgress`；

* 仅成功完成并原子提交 archive 后，清除该状态并更新最后成功日期；
* 明确区分“用户取消/进入后台”“磁盘不足”“序列化失败”“进程中断”。

“后台流式写入”解决内存，不自动解决备份一致性。主线程元数据快照后，用户或 CloudKit 可能修改同一项目；若图片和 metadata 来自不同版本，恢复后可能得到逻辑不一致的项目。

结论
v4 的证据链已基本成立，且已正确吸收上一轮的关键修正；尤其 F1 已降为待验证候选 H0，而非直接断定本案根因。但我建议暂不进入编码阶段，先补齐以下 4 个 P0 设计点。

1. 阶段划分自相矛盾。§3.1.6 把“流式二进制 archive”列为阶段 1 的 F1 修复，§4 也要求阶段 1 验收 archive 原子性；但 §7 又把新 archive 全量 round-trip 放在阶段 3。
哨兵只能阻断第二次危险重试，不能消除第一次自动 JSON 备份的 OOM 风险。请明确：阶段 1 是完整交付新 archive，还是在其完成前彻底不触发旧自动备份。
2. `automaticBackupInProgress` 必须定义成持久化状态机，不能只是一枚布尔值。进程被杀时无法记录“这是进程中断”；下次只能保守判定为“未正常结束”。状态至少应含 attempt ID、所属周、阶段、时间和结束原因；正常取消/磁盘不足/序列化错误要清理或改为 deferred，残留则只抑制该周，手动成功后才清除。否则会出现永久停备或意外自动重试。
3. 目前只定义了“备份写出”的原子性，没有定义恢复的原子性。现有恢复会先写主体数据、再逐条写 blob，过程中失败会留下半恢复状态。[BackupManager.swift (line 601)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Managers/BackupManager.swift:601) 即是这种分段落盘。新方案必须规定：验证完整 archive、版本、哈希、条目数量和解压上限后才开始替换；恢复失败时保留旧数据或具备可恢复日志。还应覆盖 ZIP 路径穿越、压缩炸弹、损坏 archive 与中断恢复测试。
4. F5 的救援界面必须在创建 `ModelContainer` 之前分支。当前容器在 `App.init()` 同步创建，[BeadInventoryApp.swift (line 37)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/BeadInventoryApp.swift:37) 至 [第 169 行 (line 169)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/BeadInventoryApp.swift:169)，且失败路径会尝试删库重建。若先开库，救援 UI 仍可能永远到不了。救援路径应只读启动标记与既有 archive，不创建主容器、`InventoryManager`，也不进入自动删库链。

其余建议：

* §4 的“一致性模型”仍是真正的阶段 1 阻塞项。校验和只能证明字节未损坏，不能证明 metadata 与图片属于同一逻辑版本；需要产品明确接受“逐记录一致”还是要求全库一致快照。

3. 200 条并非“约 2 GB 图”。当前种子每条必有一张原图、20% 另有 `finishedImage`，一半另有 display thumbnail。[BeadInventoryApp.swift (line 1448)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/BeadInventoryApp.swift:1448) 因此应以本轮实际读取的三个 blob 字段总字节数为横轴，而非项目数或“10 MB × N”估算。每轮把 `thumbnail`、`finishedImage`、`displayThumbnail` 的数量与原始字节数写入结果。

还需要调整测量解释：

* 用单调时钟记录 `performBackup()` wall time；它是主线程不可响应时长。报告 `Δfootprint = 备份窗口峰值 − 备份开始前值`，再除以实际 blob 总字节数。

结论
v2 已解决上一轮的主要方法问题；我认可 M1 的独立开关设计，也认可新 fixture 与三字段横轴。但仍有 3 个 P0，补上后才建议执行。

1. 不能用普通 Debug 构建测量后外推生产行为。Debug 的 `-Onone` 会改变对象释放时机、内存峰值和 Q4 时长，恰好影响本实验的核心指标。
应使用一个不发布的 `F1_BENCHMARK` 配置/方案：保留接近 Release 的 Swift 优化，并仅以编译标记纳入探针；不要以 `#if DEBUG` 构建的数值作为最终结论。
2. `wait_for_log(seed_completed)` 不是足够可靠的完成信号。既有事件写入的是异步、可轮转的缓存日志，[AppLogger.swift (line 123)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Managers/AppLogger.swift:123) 可能读到上一次遗留事件，也可能在被杀前未刷盘。
每次启动应传入唯一 run ID；基准探针用单独、原子落盘的结构化结果文件记录 `started`、六个检查点、当前观测最大值和 `completed`。这样中途终止才真能按 §7 作为有效结果留证。
3. 新模拟器首次灌数前必须明确关闭 CloudKit。默认配置会视为 iCloud 启用，而 seeder 会直接拒绝灌数。[BeadInventoryApp.swift (line 1413)](/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/BeadInventoryApp.swift:1413)
同理，外部 `defaults delete` 不应是唯一复位依据；增加 DEBUG-only 的“重置 weekly backup 状态”步骤并回报 run ID，避免因 simulator 偏好域路径问题导致假阴性。

还应写入计划的两点：

* T2 应改写。对已给定 blob 字节数，图片“是否可压缩”不会改变 base64 的扩张关系；噪声 PNG 的意义是构造“每像素字节较高”的合成 fixture，并非真实用户库的全局上界。
* 每轮应从同一份空白 fixture 还原，或至少清理上一轮的 `WeeklyBackups` 并检查可用磁盘。现有逻辑会保留最多 8 份 GB 级 JSON，且反复 delete 会留下 SQLite 空闲页/WAL，影响后续运行的磁盘与缓存状态。

对待决项：

* **M1：认可。**迁移关闭、备份开启是合法且必要的测量组合；我此前所说“通用名”不是要求合并为一个开关。
* **M2：需要。**并列报告 store、WAL 与三字段 blob 总字节；但 F1 拟合仍只用三字段字节，不能把 store 字节直接换算成内存阈值。
* **M3：25 条足够做 smoke/pilot。**它与 N=0 可给出初始斜率；通过后再按实际字节和磁盘余量决定是否升到 50/100/200。
