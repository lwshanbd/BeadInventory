# Error Handling Audit — PR #56

## Critical

### C1. Contrast collapse on extreme user-picked bg — no floor, no warning, entire UI text can become invisible
`/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Models/PaletteDeriver.swift:74`

`derive()` shifts every step's brightness by `(themeBg.b - refBg.b)` and clamps to `[0, 1]`. The light reference bg has `b ≈ 0.98`. If the user picks a dark color for the *light* bg slot (nothing stops them — `SwatchPickerSheet` at `ColorModeView.swift:342-365` is an unrestricted `ColorPicker`, applied live via `updateSwatch`), the entire ladder shifts down and clamps: `n900` (light ref b ≈ 0.18) goes to b = 0 — **black text on a black background**. The mirror case (near-white picked as dark bg) yields white-on-white. Because this PR routes `Text.primary/secondary/tertiary`, `Border.*`, and `Surface.subtle/strong` through this ladder (`Theme.swift:60-65, 84-90`), the failure is total: every label, chip, and divider in the app loses contrast simultaneously, including the "reset to default" UI the user would need to escape. Saturation gets a clamp (`min(..., 0.9)` at line 73, with a comment justifying it); brightness deltas get no analogous guard.

- **Hidden failure**: not an exception — a semantic silent failure. The deriver "succeeds" and returns a valid but unusable palette.
- **User impact**: one careless drag in the color picker can make the app unreadable, with recovery only via the system-drawn picker or reinstall. No log, no clamp, no warning.
- **Recommendation**: enforce a minimum brightness distance between each derived step and the target bg (or clamp `themeBg.b` into a sane band per mode before deriving, e.g. light bg b ≥ ~0.7, dark bg b ≤ ~0.35), and `logError`/assert when input falls outside it. The existing test `test_mistCoastLight_preservesContrastLadder` only checks *ordering* for a well-behaved preset — add a test with a black light-bg asserting `|n900.b − bg.b|` stays above a threshold.

## Important

### I1. Invalid stored bg hex triggers two *divergent* silent fallbacks — mismatched UI, zero logging, corruption never surfaced or repaired
`/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Models/PaletteDeriver.swift:61` and `/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Models/ColorScheme.swift:31-37`

When `resolvedLight.bg` is not valid 6-digit hex:
- `dynamicBg` (`ThemeManager.swift:92-99`) → `UIColor(themeHex:)` → falls back to **`.systemBackground`** (pure white / pure black system color).
- `neutrals(forBg:)` → `hsb(fromHex:) ?? refBg` → falls back to the **cream-latte reference ladder**.

So one bad value produces a stark white system background wearing warm beige text/chips/borders — precisely the "换主题只换背景、其余 UI 混搭" look this PR exists to eliminate — and **neither path logs anything**. The project has a `logError` convention (`InventoryManager.swift:260`) and an explicit no-silent-failure rule; this PR adds a second, deeper consumer of bg validity without adding a single diagnostic. Six months from now, a user screenshot of this mongrel UI would be undebuggable: no Sentry event, no console line, and the corrupt value persists forever because nothing repairs it.

- **How invalid data gets in**: `normalizeHex` (`ThemeManager.swift:176-179`) only strips `#` and uppercases — it validates nothing. `loadOverridesFromDefaults` (`ThemeManager.swift:228-235`) trusts raw UserDefaults strings. `SDColorScheme` hex fields ride CloudKit sync (per the Task 20 comment), so a future/older client writing e.g. 8-digit `RRGGBBAA` silently degrades every synced device.
- **Recommendation**: validate at ingestion (make `normalizeHex` reject/repair to the default palette + `logError("theme_bg_hex_invalid", metadata: [hex])` once), and keep the deriver fallback as defense-in-depth — but make both fallbacks agree (fall back to the reference *bg + ladder together*, not systemBackground for one and cream for the other).

### I2. `darkAccentFill` invalid-hex passthrough returns the worst possible value for its stated purpose — and the test canonizes it
`/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Models/PaletteDeriver.swift:96-101`

`guard let c = hsb(fromHex: hexString) else { return hexString }` — on parse failure it returns the **light** hex unchanged, so in dark mode the caller renders exactly the "刺眼的浅色块 / 发光贴片" the doc comment says this function exists to prevent, with failed white-text contrast. ### I3. `dynamicNeutral` trait closure: unmemoized full derivation + mutable-state read outside any observation/actor guarantee
`/Users/baodi/Documents/GitHub.nosync/BeadInventory/BeadInventory/Managers/ThemeManager.swift:123-130`

Two distinct issues in the trait provider closure:

1. **Recompute per resolution**: the closure calls `derivedLightNeutrals`/`derivedDarkNeutrals`, which run the full 7-step HSB derivation. 2. **Read context is unspecified**: the closure reads `self.resolvedLight/resolvedDark` (mutable, non-`@MainActor`, mutated by `updateSwatch` during live picker drags) from whatever context UIKit resolves dynamic colors in. ## Type: PaletteDeriver (enum namespace + neutrals/darkAccentFill/hsb/hex)

### Invariants Identified
- Identity property: deriving from the reference bg reproduces the Asset ladder (no visual regression) — tested
- Saturation clamps: satRatio ≤ 2.5, per-step s ≤ 0.9; brightness clamped to [0,1]
- Hue preservation: per-step hue offset relative to reference bg is carried over, normalized to [0,360)
- Invalid bg → fall back to reference ladder (documented and tested)
- `darkAccentFill`: hue preserved, b forced into [0.38, 0.50], s ≤ 0.75 → white-text AA contrast (tested)
- Internal force-unwraps (`hsb(fromHex: ref.bg)!`, `hsb(fromHex: stepHex)!`) assume reference constants are valid hex

### Ratings
- **Encapsulation**: 8/10 — caseless enum (uninstantiable), no state, `ReferenceLadder` and both reference constants private. Exactly right for a pure-function module.
- **Invariant Expression**: 7/10 — fallback semantics, clamp rationale, and the hue-offset subtlety are documented at the point they matter; the "不依赖 UIKit 便于单测" separation is expressed structurally. Docked because `hsb`/`hex` are public pure functions whose domain contracts (s,b in 0...1; h in 0..&lt;360) are comment-only.
- **Invariant Usefulness**: 9/10 — the identity property plus clamps prevent the two real bug classes here: visual regression on the default theme, and neon-tinted text on high-saturation custom bgs. Both are directly tested.
- **Invariant Enforcement**: 6/10 — runtime clamps and fallbacks are comprehensive at the `neutrals` entry point. But `hex(fromH:s:b:)` accepts any Double: a negative `h` yields a negative `hPrime` that silently falls into the `..&lt;1` branch and produces a wrong-hue (not crashed, just wrong) color; `s &gt; 1` produces out-of-gamut intermediate values rescued only by the final channel clamp. Internal callers always pre-normalize, so this is latent, not live.

### Strengths
This is the best-designed type in the PR. The reference-ladder-as-data approach makes the "default theme unchanged" invariant checkable, and the test suite (identity, ladder order, achromatic, clamping, invalid input, round-trip, WCAG contrast) is the strongest invariant enforcement in the codebase even though it's external to the type.

### Concerns
- `darkAccentFill` invalid-hex passthrough (line 97: `return hexString`) returns the garbage input, which downstream becomes `UIColor(themeHex:)`'s `.systemBackground` fallback — a background color used as an accent fill. Currently unreachable (all callers pass compile-time literals), but the fallback semantics are wrong for the accent role.
- `test_darkAccentFill_whiteTextContrast` covers 7 light hexes but `Fill` uses 10 — `748FA1` (info), `7A9B6A` (success), `C99659` (warning) are not in the contrast test list. The b-clamp makes them almost certainly pass, but the test's claim "所有 Fill 色" is currently false.
- The `h` normalization dance (`truncatingRemainder` + `if h &lt; 0`) is duplicated at line 71-72 versus the missing normalization inside `hex(fromH:)` — normalizing once inside `hex` would remove the negative-hue trap entirely.

### Recommended Improvements
- Normalize `h` (and clamp s/b) inside `hex(fromH:s:b:)`; it costs three lines and makes the public function total.
- Add the three missing semantic hexes to the contrast test.

## Type: Theme.ColorToken.Fill (Theme.swift:136-156)

### Invariants Identified
- Every Fill color: light = the design's accent light value, dark = `darkAccentFill(light)` — i.e. "dark fill is always the darkened derivation, never the Asset's lightened dark variant"
- Fill light values must equal the corresponding Asset colorset light values (Morandi.latte light == Fill.latte light)

### Ratings
- **Encapsulation**: 7/10 — the `private static func fill(_:)` helper is the right shape: the light/dark policy exists in exactly one place, and callers can't get a half-derived color.
- **Invariant Expression**: 6/10 — the doc comment explaining Fill-vs-Morandi (发光贴片 problem) is genuinely good and tells consumers *when* to use which. But the second invariant — "these literals mirror the Asset light values" — is expressed nowhere; a reader can't tell `"C8966E"` is a copy of `Palette/Peach`'s light component.
- **Invariant Usefulness**: 9/10 — this token solves a real, observed bug (white-on-lightened-accent contrast failure in dark mode) and view adoption is broad (ShippingView, StatisticsView, SettingsView, etc.).
- **Invariant Enforcement**: 3/10 — the Asset-mirror invariant is enforced by nothing. I verified today the 10 literals match the colorsets exactly (Peach C8966E, Coral C9928E, Mint 9FB089, Sky 94A8B6, Lavender B196AE, Lemon D8B97A; Semantic Error B86A60, Info 748FA1, Success 7A9B6A, Warning C99659). But the value now lives in **three** unlinked places: the colorset JSON, the `Fill` literals, and the test's hardcoded list. Retune any accent in the Asset catalog and light-mode `Morandi.latte` changes while light-mode `Fill.latte` silently keeps the old hue — a mixed-hue UI that no test catches.

### Concerns
This is the drift risk the task asked about, and it is real. It also propagates into `TabFlavor`: `.color` reads the Asset, `.fill` reads the literal — the "color and fill are the same hue family" invariant of TabFlavor depends on this unenforced mirror.

### Recommended Improvements
Pick the cheapest single-source-of-truth fix; two options, either is enough:
1. Read the light value from the Asset at runtime: resolve `UIColor(named: "Palette/Peach")` under a forced light trait, convert to hex, feed `darkAccentFill`. Removes the literals entirely; small runtime cost, cached easily.
2. Keep the literals but make them the only copy: a private `enum AccentHex { static let latte = "C8966E" ... }` referenced by `Fill`, by the test (via `@testable`), and asserted against the Asset in a unit test (`XCTAssertEqual(hexOf(UIColor(named:"Palette/Peach"), light), AccentHex.latte)`). That converts drift from silent to test-failure.

Option 2 is less invasive and I'd recommend it.

## Cross-cutting: `ColorHex = String` typealias (ColorScheme.swift:12)

Pre-existing, but this PR triples the number of APIs trafficking in it, so it's worth a verdict.

- The "RRGGBB 大写无前缀" invariant is comment-only. Nothing prevents `"#faf5ec"`, `"FAF5"`, or `"not-a-hex"` from flowing through — and all three parse layers each re-defend independently: `UIColor(themeHex:)` falls back to `.systemBackground`, `PaletteDeriver.hsb` returns nil, `neutrals` falls back to the reference ladder, `darkAccentFill` passes through.
- Concrete inconsistency this enables today: `ThemeManager.updateSwatch` → `normalizeHex` (ThemeManager.swift:176) only strips `#` and uppercases — it does **not** validate 6 hex digits. A garbage swatch persists to UserDefaults; on next launch the bg renders as `.systemBackground` (white/near-black) while the neutrals derive from the *cream-latte reference ladder*. Two different fallback policies fire for the same bad input, producing a warm-gray-on-system-white mismatch — precisely the混搭 this PR set out to eliminate. Reachable only if the color-picker path can ever emit a non-6-digit string, but the type system offers no proof it can't.
- Ratings for `ColorHex` as a type: Encapsulation 1/10, Expression 3/10 (name documents intent, guarantees nothing), Usefulness 5/10 (readability only), Enforcement 1/10.

**Recommendation (pragmatic, non-breaking-ish):** don't retrofit a full `struct ColorHex` across the codebase in this PR. Two cheaper moves:
1. Make `normalizeHex` validating (reject/clamp to previous value on non-6-hex input) — that closes the only real user-controlled entry point, and then every internal `ColorHex` is valid by construction of the pipeline.
2. If you later want the compile-time guarantee, a `struct ColorHex { let raw: String; init?(_ raw: String) }` with `Codable` conformance would let `ColorPalette`, `DerivedNeutrals`, and the deriver drop all four scattered fallback paths — a good follow-up, poor fit for this already-large diff.

## Cross-cutting: `fileprivate Palette` (Theme.swift:49)

The access modifier still compiles and still does its literal job — no code outside Theme.swift references `Palette.*`. But the encapsulation is now largely **nominal**: the actual protected resource is the asset-name strings, and those are used raw in four other places in the same file (`Decorative.latte`, `Morandi.*`, `Interactive.primaryFallback`, `Border.emphasisFallback` all say `Color("Palette/Peach")` instead of `Palette.peach`) and in TabFlavor.swift (4 more). So the fence stands while the gate is open. Meanwhile the *new* members (`n50…n900` routing through `ThemeManager.dynamicNeutral`) are the part where `fileprivate` genuinely earns its keep — Text/Surface/Border consume them and business code cannot shortcut to a stale static neutral. Verdict: keep `fileprivate`, but route the same-file string literals through `Palette.*`, and either give TabFlavor a sanctioned accessor (e.g. expose the four flavor colors from `ColorToken`) or accept and document that TabFlavor is part of the design-system boundary.
