  ### 问题
  1. **E1 可能被打破：超时失败会继承上一轮的「空库」标志。** 超时处理在 :1724-1757，它直接调用 `finishInitialLoadFailure`，既不经过 `applyInitialPersistentLoad`，也不经过 `finishInitialLoadSuccess`，所以 `initialLoadFoundUnexpectedEmptyStore` 不会被清掉。可能的过程：
     - 第一轮读到空库，标志变成 true，同时安排自动重试；
     - 下一轮自动重试超时，报错消息换成「云端数据仍在同步中」，标志还是 true；
     - ContentView.swift:142-144 于是显示「本机的同步数据已被系统清除」，还给出「从备份恢复」。
     
     实际上这次是超时，不是清库。触发概率不高，但一旦触发就是引导用户往库里写备份，后面可能叠出重复数据。
  2. 放行标志可能残留，也可能被浪费。`acceptEmptyStoreForBackupRestore` 打开它以后调用 `retryInitialLoad`。如果这一轮在进入 apply 之前就失败了（比如超时，或者 :1215 的「没有 model context」提前返回），标志会留到后面的某一轮才被用掉。这只在本次进程内有效，也确实是用户已经确认过的意图，风险低。同一路径下，ContentView 的 `pendingBackupRestore`（ContentView.swift:32、:273-277）也会一直挂着，后面任何一次加载成功都会突然弹出恢复页。
  3. ContentView 的 `isICloudSignedOut`（ContentView.swift:389-399）在 `.pausedNoICloud` 下判断的是 `accountStatus != .available`。所以账号状态还没查回来（nil）时，就已经算作「未登录」，界面会给出「从备份恢复」。如果用户只是关了 iCloud 云盘，在查回来之前点了恢复，正好就是注释里想避免的「叠成两份」。
  
  ### 建议
  - **主要建议**：让「空库」标志只能跟着失败原因一起写入。最小改法是给 `finishInitialLoadFailure` 加一个参数，在函数开头统一赋值：
    ```swift
    private func finishInitialLoadFailure(userMessage: String, isUnexpectedEmptyStore: Bool = false, metadata: ...)
    ```
    这样所有失败路径（包括超时）都会自动把它设成 false，E1 就不再依赖调用顺序了。:2097 那一行也随之删掉。再往前一步，可以把两个字段合成一个 `initialLoadFailure: (message: String, kind: Kind)?`。但这会牵动现有对 `initialLoadErrorMessage` 的读取，看你们愿不愿意多改一些。
  - 放行标志可以保持现状。如果想收紧，就在 `finishInitialLoadFailure` 里一并清掉 `allowUnexpectedEmptyStoreOnce`。ContentView 那边在 `initialLoadErrorMessage` 再次变为非 nil 时，把 `pendingBackupRestore` 复位。
  - `isICloudSignedOut` 在 paused 分支改成 `accountStatus != nil && accountStatus != .available`，或者干脆写成 `== .noAccount`。账号查回来之前不给恢复入口。代价是这段时间界面会显示通用的报错文案。
  
  ## 总体
  方向是对的：用 enum 的 case 表达模式，可变状态都是 private(set)，有唯一的入口。最值得改的两处都很小：
  1. 「空库」标志要跟失败原因绑在一起写，不然超时后会显示错误的原因、给出错误的恢复入口；
  2. `ICloudBootGuard` 的判断抽成纯函数补测试，并在文档里写明「第一次退出 iCloud 那次启动挡不住」。
  
  其余几条（mode 在各分支直接赋值、否定比较改成显式 switch、`bootValue` 改名）是顺手的清理。

  **建议**：至少在 `.iCloudEnabled` 模式下查到 `.noAccount`、而且这次启动是靠「token 不可靠」标记才开的 CloudKit 时，打一条 warning 或 error，比如 `cloudkit_enabled_without_account_purge_likely`。界面上也应该提示一句「请勿在未登录状态下继续使用，重新登录 iCloud 后再打开」。PR 描述和 `ICloudBootGuard` 的注释里，应该把这个已知缺口写明白。现在注释写的是「免得用户真退出 iCloud 时还开着 CloudKit 被清库」，读起来像已经防住了，其实只防住了第二次启动。
  
  ### 3. 【中】暂停模式下，账号「查不到」也当成「没登录」。会显示「未登录 iCloud」，还给出「从备份恢复」
  **位置**：`ContentView.swift:391-392`（`isICloudSignedOut` 的 `.pausedNoICloud` 分支）、`BeadInventoryApp.swift:1052`（查询出错时 `accountStatus = .couldNotDetermine`），以及 `:938`、`:966-971` 的状态文案
  
  **场景**：用户其实登录着 iCloud，只是关了 iCloud 云盘。这次启动时没网，或者 cloudd 报错，账号状态变成 `.couldNotDetermine`。状态也可能还没查回来（nil），或者是 `.temporarilyUnavailable`。这时 `accountStatus != .available` 成立，界面标题是「未登录 iCloud」，主按钮是「从备份恢复」。用户照着恢复了，下次联网查到 `.available`，标记被设成 true，再下次启动开了 CloudKit，云端数据同步回来，就跟备份叠成两份。这正是代码注释自己说要避免的。另外 `record` 对 `.temporarilyUnavailable` 和 `.couldNotDetermine` 什么都不做（`default: break`）。所以长期处在这两种状态的用户，每次启动都会被暂停同步，设置页一直写着「未登录 iCloud」，跟事实不符。
  
  **建议**：只有 `accountStatus == .noAccount` 时才算「没登录」。nil、`.couldNotDetermine`、`.temporarilyUnavailable` 走「无法确认 iCloud 状态」的文案，不给恢复入口，或者先让用户重试查询。暂停模式的文案也按 `lastErrorMessage` 区分一下。
  
  ### 4. 【中】空库是在用户选好备份之前就放行的。关掉恢复页或者没有备份，App 就变成一个能正常写入的空库
  **位置**：`ContentView.swift:225-226`、`InventoryManager.swift` 里的 `acceptEmptyStoreForBackupRestore`
  
  **场景**：
  - 用户点「选择备份」后，恢复页打开了，但里面一个备份也没有（`backups.isEmpty`）。也可能用户看了一眼点「关闭」。这时空库已经被当成正常加载完成，`isDataLoaded = true`，写入全部放开。
  - 用户随手加一个品牌，这条就落盘了。之后 `allEmpty` 不再成立，「本机库被清空」的检查下次启动也不会再拦。等用户重新登录 iCloud，云端的老数据跟这些新数据混在一起，用户也没收到任何提示。确认弹窗只警告了「恢复后」可能重复，没提「不恢复也会这样」。
  
  **建议**：弹确认框之前，先用 `BackupManager.getBackupList()` 看有没有备份，没有就不显示这个按钮，或者换成说明文字。更好的做法是把「接受空库」推迟到用户真正选中某个备份、点下恢复的那一刻。如果做不到，关掉恢复页时没有恢复成功的话，至少要回到报错页，或者记一条 warning（`backup_restore_dismissed_with_empty_store_accepted`）。
  
  ### 5. 【中】清库报错页仍然保留「以本地模式继续」，进去以后什么都存不下，也没有提示
  **位置**：`ContentView.swift:191`
  
  **场景**：在「未登录 iCloud」页点「以本地模式继续」，会进入 `isUsingLocalFallbackMode`。内存是空的，之后每次保存都被 `save_skipped_local_fallback_mode` 拦下，只记一条 warning。用户以为在正常使用，录进去的东西重启就没了。这个本地模式是以前就有的。但在清库这种情况下，库里本来就没东西可以浏览，这个按钮只剩一个作用：让用户白录一遍。
  
  **建议**：`isClearedAfterICloudSignOut` 为 true 时隐藏这个按钮。
  
  ### 6. 【低】暂停模式下容器打不开时，回退日志里丢了「暂停」这个原因
  **位置**：`BeadInventoryApp.swift:150-157`
  
  `pausedForMissingICloud` 为 true 时，`cloudConfiguration` 本来就是 `.none`。它失败以后，代码会用一份一模一样的 `localFallbackConfiguration` 再试一次。日志 `model_container_fallback_to_local` 只带 `userOptedOut: false`，看起来像是「CloudKit 容器初始化失败」，其实这次 CloudKit 根本没开。上面那句注释（「userOptedOut=false 时这里才是被动 fallback」）也不对了。建议 metadata 里加上 `pausedNoICloud: pausedForMissingICloud`。最后 mode 落到 `.localFallback`，用户看不到「未登录 iCloud」的提示，这一点可以接受。
  
  ### 7. 【低，建议核实】以 `.none` 打开原来带 CloudKit 的库，之后能不能补同步
  **位置**：`BeadInventoryApp.swift` 里 `cloudKitDatabase: useCloudKit ? .automatic : .none`
  
  PR 假设暂停期间本机的改动，重新登录后会按规则跟云端合并。这要看 SwiftData 在 `.none` 下是不是还开着 persistent history tracking。没开的话，这段时间的改动不会被导出到 CloudKit。Core Data 还可能报「Store opened without NSPersistentHistoryTrackingKey」，把库变成只读。`userOptedOut` 那条路径以前就是这么打开的，所以这不是新问题。但这次会有更多用户被动进入这条路径。建议在模拟器上走一遍：暂停期间改一条库存，登录 iCloud，重开 App，看改动有没有上云。
